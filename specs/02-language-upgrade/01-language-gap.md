# 01 - The Language Gap: Python 3.4 → 3.15

## Overview

This file enumerates every language-level change between Python 3.4 (gpython's
current baseline) and Python 3.15, and specifies the parser and compiler work
each one implies.

The changes are grouped by the workstream they touch, because the workstreams
have different risk profiles:

- **Grammar** - new syntax the parser must accept.
- **Compiler** - new bytecode semantics, new opcodes, changed code-object
  layout.
- **Runtime** - new types, changed builtins, changed evaluation order.

The PEP numbers are the authoritative identifiers. Every claim marked
**verified** was checked against a fetched source; the verification command is
given in the Verification section.

The reference release is **CPython 3.15.2**, pinned by tag. The grammar used
here is `Grammar/python.gram` at that tag, and the token list is
`Grammar/Tokens`.

### The parser situation

**gpython uses a hand-written lexer plus a goyacc grammar** (`parser/grammar.y`,
`parser/y.go`, generated by `go generate ./parser/`).

**CPython 3.9 replaced its LL(1)-style parser with a PEG parser** (PEP 617).
The grammar now lives in `Grammar/python.gram` and the generator in
`Tools/peg_generator/`.

**This is a decision point, not a mandate.** gpython does not have to adopt PEG.
The PEG parser is an implementation strategy, not a language feature. The
language features are what must be implemented.

However, three of the 3.12+ features are much easier with PEG than with an
LL(1)-style parser:

1. **PEP 701 (f-string formalisation)** requires arbitrary expressions inside
   `{}`, including nested f-strings with the same quote character, backslashes,
   and comments. An LL(1) parser cannot do this without a separate lexer mode
   per nesting level.
2. **PEP 810 (`lazy import`)** is a soft keyword. Soft keywords need
   contextual lexing, which PEG's `&"lazy"` lookahead handles naturally.
3. **PEP 634 (pattern matching)** has an inherently ambiguous grammar that
   benefits from PEG's ordered-choice semantics.

**Recommended:** keep the goyacc grammar and extend it, rather than porting the
PEG generator. The cost of the PEG port is high and the benefit is
maintainability, not capability. But see the `lazy` keyword note below - that
one may force a lexer change.

**Verified: the 3.15.2 grammar uses a soft keyword for `lazy`.** From
`Grammar/python.gram`:

```
    | &('import' | 'from' | "lazy") import_stmt
...
    | lazy="lazy"? 'import' a=dotted_as_names { _PyAST_Import(a, lazy ? 1 : 0, EXTRA) }
```

The `&("lazy")` lookahead is the PEG idiom for a soft keyword: it matches
`lazy` only when the following token can legally follow it. gpython's lexer
will need an equivalent - a token that is `NAME` when not followed by `import`
or `from`, and `LAZY` when it is.

**Comprehension inlining (PEP 709) is the compiler change with the widest
reach.** Before 3.12, a list comprehension compiled to a nested function that
the enclosing code called. After 3.12, it compiles to inline code. This changes:

- The bytecode shape of every comprehension.
- The scoping: a comprehension no longer has its own function scope, so
  `locals()` behaviour and closure semantics change.
- Tracebacks: a comprehension no longer shows a `<listcomp>` frame.
- Performance: comprehension bodies are now specialised by the interpreter.

gpython's `compile/` package must be reworked for this.

### The UTF-8 default encoding (PEP 686)

This is the change most likely to break existing gpython code, and it is worth
calling out separately.

Before 3.15, the default encoding for `open()`, `locale.getpreferredencoding()`
and several other paths was platform-dependent (UTF-8 on most Linux systems,
but not guaranteed). From 3.15 the default is **UTF-8 everywhere**.

Affected surfaces in gpython:

- `open()` with no `encoding` argument.
- `locale.getpreferredencoding()`.
- `sys.getdefaultencoding()` - this still returns `'utf-8'`, unchanged.
- `str.encode()` / `bytes.decode()` with no argument - still UTF-8, unchanged.
- The `PYTHONUTF8` environment variable and the `-X utf8` flag.
- `sys.stdout.encoding` when the locale is not UTF-8.

gpython's `stdlib/os` and any file-handling code must be audited for
locale-dependent encoding lookups.

### The annotation model change (PEP 649/749)

This is the single most invasive runtime change in the 3.14 → 3.15 window.

Before 3.14, annotations were evaluated **at definition time** and stored as
objects in `__annotations__`.

From 3.14 (PEP 649), annotations are evaluated **lazily**:

- The compiler emits an `__annotate__` function on the class or function.
- `__annotations__` becomes a **descriptor**, not a plain dict.
- Accessing `__annotations__` triggers the evaluation.
- `annotationlib.get_annotations(obj, format=...)` is the explicit API.

The three annotation formats:

| Format | Meaning |
|---|---|
| `annotationlib.Format.VALUE` | The evaluated object (the old behaviour) |
| `annotationlib.Format.STRING` | The source text as a string |
| `annotationlib.Format.FORWARDREF` | A `ForwardRef` that resolves on use |

PEP 563 (`from __future__ import annotations`) is **superseded** by PEP 649.
The `__future__` import still works but the mechanism is different.

For gpython this means the compiler must emit an `__annotate__` function
alongside each annotated definition, and the runtime must support a descriptor
on the module type.

### The pattern matching surface (PEP 634/635/636)

If gpython is to run modern Python, pattern matching is mandatory. The AST
nodes are:

| Node | Matches |
|---|---|
| `MatchValue` | A literal value compared with `==` |
| `MatchSingleton` | `None`, `True`, `False` (identity) |
| `MatchSequence` | A sequence, matched positionally |
| `MatchMapping` | A mapping, matched by key |
| `MatchClass` | A class, matched by attribute |
| `MatchStar` | `*rest` in a sequence pattern |
| `MatchAs` | A capture pattern or `x as y` |
| `MatchOr` | `A | B` alternatives |

The `match` statement itself is a `Match` node with `cases`, each a
`match_case` with `pattern`, `guard` and `body`.

### The 3.15 `lazy import` (PEP 810)

`lazy import x` and `lazy from x import y` defer the import until the module is
first accessed.

The constraints, from the 3.15.2 grammar and the PEP:

- Module level only - not inside a function, class or comprehension.
- Not allowed in `try`/`except`/`finally`.
- Not allowed with `*` (`from x import *`).
- Not allowed with `__future__` imports.

The runtime support is the `_PyImport_LazyImportModuleLevelObject` and
`_PyImport_TryLoadLazySubmodule` C API, and the `_imp._set_lazy_attributes`
Python-level hook, all of which are described in
`01-module-system/02-module-object-model.md`.

**The lazy import feature depends directly on the module system work.** This
is the clearest dependency between the two workstreams in the whole spec set.

## Verification

**1. Confirm the reference grammar has the expected 3.15 productions.**

```bash
G=$(mktemp)
curl -s -o $G https://raw.githubusercontent.com/python/cpython/v3.15.2/Grammar/python.gram
grep -n 'lazy="lazy"?' $G          # PEP 810
grep -n 'TSTRING_START' $G          # PEP 750
grep -n 'except_star_block' $G      # PEP 654
grep -n '"type" type_alias' $G      # PEP 695
```

**2. Confirm the token list.**

```bash
curl -s https://raw.githubusercontent.com/python/cpython/v3.15.2/Grammar/Tokens \
  | grep -E 'TSTRING|LAZY'
```

Expect `TSTRING_START`, `TSTRING_MIDDLE`, `TSTRING_END`. Expect **no** `LAZY`
token - `lazy` is a soft keyword handled in the grammar, not the lexer.

**3. Confirm the `Import` AST node has a `lazy` field in 3.15.**

The authoritative AST definition is `Parser/Python.asdl`, not `Lib/ast.py`
(which merely re-exports from the C `_ast` module):

```bash
curl -s https://raw.githubusercontent.com/python/cpython/v3.15.2/Parser/Python.asdl \
  | grep -E "Import\(|Match|type_param"
```

Expect:

```
          | Import(alias* names, int? is_lazy)
...
    pattern = MatchValue(expr value)
            | MatchSingleton(constant value)
            | MatchSequence(pattern* patterns)
            | MatchMapping(expr* keys, pattern* patterns, identifier? rest)
            | MatchClass(expr cls, pattern* patterns, identifier* kwd_attrs, pattern* kwd_patterns)
            | MatchStar(identifier? name)
            | MatchAs(pattern? pattern, identifier? name)
            | MatchOr(pattern* patterns)
...
    type_param = TypeVar(identifier name, expr? bound, expr? default_value)
               | TypeVarTuple(identifier name, expr? default_value)
```

Note the field is named **`is_lazy`**, not `lazy`. Note also that
`MatchMapping` has an `identifier? rest` field, and `MatchClass` has the
`kwd_attrs`/`kwd_patterns` pair.

**4. Confirm the pattern-matching AST nodes exist.**

```bash
curl -s https://raw.githubusercontent.com/python/cpython/v3.15.2/Parser/Python.asdl \
  | grep -E "^\s+\| Match|^    pattern = "
```

Expect `Match` (the statement) plus all nine `pattern` alternatives.
