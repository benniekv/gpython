# 04 - Code Style, Test Infrastructure and Test Data

## Overview

This file records how gpython looks and how it is tested, so that new code
matches the existing conventions. It also answers the data question: where
does the test data come from, and what should be used when new data is needed.

The findings that matter most for a port:

1. **The golden files are the test oracle, and they were generated by
   CPython 3.4.** Every generator script in the repo starts with
   `#!/usr/bin/env python3.4`. To move to 3.15, the golden files must be
   regenerated with CPython 3.15, and that will change many of them.
2. **gpython has no "expected output" fixture mechanism beyond golden
   files.** There is no `expected/` directory, no snapshot framework, no
   property-based testing. The one extension point is `pytest.RunScript`.
3. **CPython's own test data is the natural source of new fixtures**, and
   504 data files across 27 directories are available under `Lib/test/`.
4. **The comment style is documentation-grade.** 92% of exported functions
   have a preceding comment. New code must match that.

## Spec

### The code style

#### The licence header

Every Go file starts with exactly two comment lines:

```go
// Copyright 2018 The go-python Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.
```

Note the **two spaces** after the period in "Authors.  All rights reserved."
This is the GNU style, not Go's usual one space. Reproduce it exactly.

Measured across the 91 non-test `.go` files:

| Copyright year | Files |
|---|---|
| 2018 | 74 |
| 2019 | 1 |
| 2022 | 11 |
| 2023 | 3 |

**The year is the year the file was created, not the current year.** New
files should carry the year they are added.

**Two files deviate, and both deviations are explainable.** They are the
exceptions, not the rule:

| File | Deviation |
|---|---|
| `ci/run-tests.go` | Uses `// Copyright ©2018 The go-python Authors. All rights reserved.` - a copyright symbol and a **single** space. |
| `repl/web/serve.go` | Has **no** header. It is behind `//go:build none`, so it is disabled dead code. |

Every other non-test file uses the two-space form. Do not follow the
`ci/run-tests.go` variant.

The Python test files carry the same header, but as a `#` comment:

```python
# Copyright 2018 The go-python Authors.  All rights reserved.
# Use of this source code is governed by a BSD-style
# license that can be found in the LICENSE file.
```

#### Comment style

Measured across the 91 non-test `.go` files:

| Style | Count | Notes |
|---|---|---|
| `//` fragment or identifier reference | 3,074 | The dominant style: `// The call to foo`, `// Return the value` |
| `//` sentence comment | 2,355 | Starts with a capital letter and reads as a sentence |
| `//` blank | 376 | Section separators inside functions |
| `// TODO` or `// FIXME` | 155 | Active markers |
| `/* ... */` block | 180 | Used for multi-line explanations and for the build tags |

**The rules that emerge:**

- Comments are `//` line comments by default. A `/* */` block is used when
  the comment is genuinely multi-line, such as the explanation above a
  function's contract.
- A comment above a declaration starts with a **capital letter** and reads as
  a sentence. It does **not** end with a period when it is a fragment
  describing an identifier.
- A comment inside a function is lower-case and terse.
- `TODO` and `FIXME` are written as `// TODO: ...` or `// FIXME ...`.
  There are 155 of them. They are load-bearing: the `py/tests/*.py` files use
  `# FIXME` to mark assertions that gpython cannot yet satisfy.
- **Exported functions are documented.** Of 206 exported `func`s, 189 have a
  preceding comment, which is 92%.

Example of the house style, from `pytest/pytest.go`:

```go
// Compile the program in the file prog to code in the module that is returned
func compileProgram(t testing.TB, prog string) (*py.Module, *py.Code) {
```

Note: no trailing period, because it is a fragment describing what the
function returns.

#### Naming

| Kind | Convention | Example |
|---|---|---|
| Exported function | `CamelCase` | `RunTests`, `CompileSrc` |
| Unexported function | `camelCase` or `snake_case` | 265 functions use an internal underscore |
| Exported type | `CamelCase` | `ModuleImpl`, `SymTable` |
| Unexported type | `camelCase` | 26 types |
| Private type | `I__dunder__` | `I__add__`, `I__getitem__` |
| Test function | `Test<Thing>` | `TestString`, `TestMath` |
| Test data file | `test.py` and `test_golden.txt` | in a `testdata/` directory |

**The `I__dunder__` convention is the one to know.** gpython maps Python's
dunder methods to Go interface methods named `I__<name>__`. 87 distinct
dunder methods are implemented this way:

```
I__add__  I__and__  I__bool__  I__bytes__  I__call__  I__ceil__
I__contains__  I__del__  I__delattr__  I__delete__  I__delitem__
I__dir__  I__divmod__  I__enter__  I__eq__  I__exit__  I__float__
I__floor__  I__floordiv__  I__format__  I__ge__  I__get__
I__getattr__  I__getattribute__  I__getitem__  I__gt__  I__hash__
I__iadd__  ...
```

The `I__` prefix avoids colliding with Go's own keywords and makes the
mapping explicit at the call site.

#### Error handling

Measured across the 91 non-test `.go` files:

| Mechanism | Count |
|---|---|
| `panic(...)` | 105 |
| `fmt.Errorf(...)` | 16 |
| `errors.New(...)` | 6 |

**gpython panics for programmer errors and returns errors for expected
failures.** The `panic` count dominates, which is a deliberate style choice:
the interpreter is a closed system where an internal inconsistency is a bug,
not a runtime condition. Python-level exceptions are raised through the
`py` package's exception machinery, not through Go error returns.

**The exception to the rule is the test harness.** `pytest/pytest.go` returns
`error` values rather than panicking, because `testing.T` needs the error
reported rather than the process killed.

### The test infrastructure

gpython has **five** distinct test styles. Which one to use depends on what
is being tested.

#### Style 1: Go unit tests for the `py` package

`py/tests/*.py` are **Python** files run through the harness, and the Go
side is `py/py_test.go`. The convention:

```go
func TestString(t *testing.T) {
	pytest.RunTests(t, "tests")
}
```

`pytest.RunTests` finds every `*.py` in the directory **except** files
starting with `lib`, compiles each one, and runs it. The test passes if the
script does not raise.

The Python-side convention is a `doc` variable that must be set to
`"finished"`:

```python
doc="str()"
assert str() == ""
assert str("hello") == "hello"
```

`pytest.run` checks:

```go
	if doc, ok := module.Globals["doc"]; ok {
		if docStr, ok := doc.(py.String); ok {
			if string(docStr) != "finished" {
				t.Fatalf("Didn't finish at %q", docStr)
			}
		}
```

**The `doc` variable is a progress marker.** It names the section currently
being tested, so a failure says which section broke. It must be set before
every group of assertions.

The helper module is `py/tests/libtest.py`:

```python
def assertRaises(expecting, fn, *args, **kwargs):
    """Check the exception was raised - don't check the text"""
    try:
        fn(*args, **kwargs)
    except expecting as e:
        pass
    else:
        assert False, "%s not raised" % (expecting,)

def assertRaisesText(expecting, text, fn, *args, **kwargs):
    """Check the exception with text in is raised"""
    try:
        fn(*args, **kwargs)
    except expecting as e:
        assert text in e.args[0], "'%s' not found in '%s'" % (text, e.args[0])
    else:
        assert False, "%s not raised" % (expecting,)
```

**Note the `lib` prefix.** `pytest.findFiles` skips files starting with
`lib`, which is how the helper module is excluded from the test run.

#### Style 2: Go unit tests for the runtime internals

`py/args_test.go`, `py/py_test.go`, `parser/lexer_test.go`,
`parser/stringescape_test.go`, `compile/instructions_test.go`. These are
ordinary Go tests with `testing.T`, and they use `github.com/google/go-cmp/cmp`
for structural comparison.

#### Style 3: The stdlib module golden-file test

**This is the pattern to follow for every new stdlib module.** It is used by
**seven** modules: `array`, `binascii`, `glob`, `os`, `string`, `tempfile` and
`time`.

`math` is the exception: it has no `testdata/` directory. Its tests live in
`stdlib/math/tests/` as a multi-file suite in CPython's own style.

The layout:

```
stdlib/<module>/
    <module>.go          the implementation
    <module>_test.go     the Go test, usually 13 lines
    testdata/
        test.py          the Python test script
        test_golden.txt  the expected combined stdout+stderr
```

The Go test is:

```go
// Copyright 2022 The go-python Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package string_test

import (
	"testing"

	"github.com/go-python/gpython/pytest"
)

func TestString(t *testing.T) {
	pytest.RunScript(t, "./testdata/test.py")
}
```

Note `package string_test`, an **external test package**, so the test
exercises the public API only.

The Python script mixes prints and asserts:

```python
import string

print("globals:")
for name in ("whitespace",
		"ascii_lowercase",
		...):
    v = getattr(string, name)
    print("\nstring.%s:\n%s" % (name,repr(v)))

def assertEqual(x, y):
    assert x == y, "got: %s, want: %s" % (repr(x), repr(y))

assertEqual(string.capwords('abc def ghi'), 'Abc Def Ghi')
```

**The prints produce the golden file; the asserts are checked in-band.** An
assertion failure aborts the script, so the golden file comparison never runs
and the test fails with the assertion message. A `print` mismatch produces a
diff.

The golden file is the **combined stdout and stderr**:

```go
	sys.Globals["stdout"] = &py.File{File: out, FileMode: py.FileWrite}
	sys.Globals["stderr"] = &py.File{File: out, FileMode: py.FileWrite}
```

Both are redirected to one file, so ordering between them is preserved. The
comparison normalises CRLF:

```go
	want = bytes.ReplaceAll(want, []byte("\r\n"), []byte("\n"))
```

and uses `cmp.Diff` for the error message:

```go
	diff := cmp.Diff(string(want), string(got))
	if !bytes.Equal(got, want) {
		out := fileBase + ".txt"
		_ = os.WriteFile(out, got, 0644)
		return fmt.Errorf("output differ: -- (-ref +got)\n%s", diff)
	}
```

#### Style 4: The compiler, symtable and grammar golden data

**This is the most important style for the 3.15 work**, because it is where
the language-level changes are verified.

Three generators, three data files:

| Generator | Data file | Oracle |
|---|---|---|
| `compile/make_compile_test.py` | `compile/compile_data_test.go` | CPython's `compile()` output: the full `py.Code` struct |
| `symtable/make_symtable_test.py` | `symtable/symtable_data_test.go` | CPython's `symtable.symtable()` output |
| `parser/make_grammar_test.py` | `parser/grammar_data_test.go` | CPython's `ast.parse()` + `ast.dump()` output |

**All three generators start with `#!/usr/bin/env python3.4`.** They must be
run with a CPython **3.4** interpreter to reproduce the existing data, and
with a CPython **3.15** interpreter to produce the new data.

The compile generator's case list is a `inp` array of tuples:

```python
inp = [
    # Constants
    ('''1''', "eval"),
    ('''"hello"''', "eval"),
    # BinOps - strange operations to defeat constant optimizer!
    ('''"a"+1''', "eval"),
    ...
    # assign
    ('''a = 1''', "exec"),
    ('''f() = 1''', "exec", SyntaxError),
]
```

The third element is the expected exception type, if any.

The compile generator dumps the code object field by field:

```python
            "&py.Code{",
            "Argcount: %s," % x.co_argcount,
            "Kwonlyargcount: %s," % x.co_kwonlyargcount,
            "Nlocals: %s," % x.co_nlocals,
            "Stacksize: %s," % x.co_stacksize,
            "Flags: %s," % x.co_flags,
            "Code: %s," % string(x.co_code),
            "Consts: %s," % consts(x.co_consts),
            "Names: %s," % strings(x.co_names),
            "Varnames: %s," % strings(x.co_varnames),
            "Freevars: %s," % strings(x.co_freevars),
            "Cellvars: %s," % strings(x.co_cellvars),
            "Filename: %s," % string(x.co_filename),
            "Name: %s," % string(x.co_name),
            "Firstlineno: %d," % x.co_firstlineno,
            "Lnotab: %s," % string(x.co_lnotab),
            "}",
```

**This is the contract for the 3.15 work.** The `py.Code` struct must grow
the fields that 3.15 adds: `co_posonlyargcount`, `co_qualname`, the
`CO_*` flag bits for `CO_FUTURE_ANNOTATIONS` and friends, and the
`co_exceptiontable` that replaces `co_lnotab` for the 3.11 exception
machinery. The generator and the data file change together.

The symtable generator reads CPython's internal bitfields, which are not
exported:

```python
try:
    # run ./build.sh in the readsymtab directory to create this module
    from readsymtab import readsymtab
    use_readsymtab = True
except ImportError:
    import ctypes
    use_readsymtab = False
    print("Using compiler dependent code to read bitfields - compile readsymtab module to be sure!")
```

and falls back to `ctypes` to poke at the struct:

```python
        # FIXME compiler dependent!
        base_addr = id(st._table) + ctypes.sizeof(ctypes.c_long)*8+ ctypes.sizeof(ctypes.c_int)*3
        flags = int.from_bytes(ctypes.c_int.from_address(base_addr), sys.byteorder)
```

**This will not work on CPython 3.15.** The `PySTEntryObject` layout changed
between 3.4 and 3.15. The `readsymtab` C extension must be updated, and the
`ctypes` fallback must be deleted or rewritten, because poking at a struct
layout by offset is fragile across versions.

The grammar generator dumps the AST:

```python
def dump(source, mode):
    """Dump source after parsing with mode"""
    a = ast.parse(source, mode=mode)
    return ast.dump(a, annotate_fields=True, include_attributes=False)
```

**`ast.dump` output changed between 3.4 and 3.15.** Every grammar golden
file entry will change. The 3.15 AST has the `is_lazy` field on `Import`,
the `type_params` field on `FunctionDef` and `ClassDef`, and nine new
`Match*` node types.

#### Style 5: The benchmark harness

`pytest.RunBenchmarks` runs a directory of Python files under `testing.B`.
The `stdlib/math/tests/` directory shows the larger form: a multi-file test
suite with `libtest.py`, `testcases.py` and `mathtests.py` in the style of
CPython's own `Lib/test/test_math.py`.

### The test data: where it comes from

#### The data already in gpython

| Location | Files | Source |
|---|---|---|
| `py/tests/*.py` | 23 | Hand-written, one per `py` package feature |
| `stdlib/*/testdata/test.py` | 7 | Hand-written, one per tested stdlib module |
| `stdlib/math/tests/*.py` | 4 | Ported from CPython's `Lib/test/test_math.py` style |
| `compile/compile_data_test.go` | ~250 cases | **Generated by CPython 3.4** |
| `symtable/symtable_data_test.go` | ~90 cases | **Generated by CPython 3.4** |
| `parser/grammar_data_test.go` | ~400 cases | **Generated by CPython 3.4** |
| `testdata/hello.py` + `hello_golden.txt` | 2 | The smoke test |

**So the data is in two categories: hand-written tests, and CPython-generated
golden files.** There is no third category. There are no external datasets.

#### The `-regen` flag

The golden files can be regenerated from gpython's own output:

```go
var RegenTestData = flag.Bool("regen", false, "Regenerate golden files from current testdata.")
```

```go
	if *RegenTestData {
		err := os.WriteFile(task.GoldFile, got, 0644)
```

**This flag is a trap during the 3.15 work.** Running the tests with
`-regen` would rewrite the golden files from gpython's output, baking the
3.4 behaviour in as the new expected result. The golden files must be
regenerated from **CPython 3.15**, not from gpython.

The correct procedure is:

1. Install CPython 3.15.
2. Run the three generators with it: `python3.15 make_compile_test.py`,
   `python3.15 make_symtable_test.py`, `python3.15 make_grammar_test.py`.
3. Review the diff. Every change should be explainable by a 3.5 to 3.15
   language change.
4. Commit the regenerated data **with** the code change that makes gpython
   match it.


**The recommendation for module testing is CPython's own data, not an
external dataset.** The reason is that the expected outputs must be
*computable by a Python interpreter*. An external dataset has no expected
output; a CPython test data file has the expected output embedded in the
test that uses it. For example `Lib/test/decimaltestdata/*.decTest` carries
its own expected results, and `Lib/test/xmltestdata/` carries the expected
serialised form.

**The second recommendation is to use CPython's test *modules*, not just its
data.** `Lib/test/test_<module>.py` is the specification of what the module
must do, with the expected values inline. gpython's `stdlib/math/tests/`
already follows this pattern.

#### External datasets, when they are the right answer

An external dataset is appropriate when the test needs **volume** rather
than **correctness of a known answer**. Examples:

| Need | Dataset | Where | Why |
|---|---|---|---|
| Large text for `str`, `re`, `textwrap` | Any large plain-text corpus | Project Gutenberg, or the `text` dataset on Kaggle | Exercises the string algorithms at scale and finds pathological cases |
| Large CSV for `csv` | Any real CSV | Kaggle, or the `csv` sample data repos | Exercises quoting, embedded newlines and dialects |
| JSON for `json` | Any real JSON | Kaggle | Exercises nesting, unicode escapes and number formats |
| Unicode text for `codecs` | The Unicode Character Database | `https://www.unicode.org/Public/UCD/latest/ucd/UnicodeData.txt` | Exercises every codepoint |
| Locale data for `locale` | CLDR | `https://cldr.unicode.org/` | Exercises locale-sensitive formatting |
| Timezone data for `zoneinfo` | The IANA database | `https://www.iana.org/time-zones` | Exercises DST transitions |

**Kaggle specifics.** Kaggle datasets normally require an account and an
accepted licence to download, which makes them unsuitable for a CI-run
regression suite. The datasets that work well are the ones that can be
fetched by URL without authentication.

**The rule to follow: a dataset that goes into the repository must be
small enough to commit.** gpython's golden files are committed. A
multi-megabyte Kaggle download does not belong in the tree. The pattern
that works:

1. Take a **small, curated slice** of the dataset (a few KB).
2. Commit it under `stdlib/<module>/testdata/`.
3. Generate the golden file from CPython 3.15.

This gives a deterministic, offline, licence-clean test.

**The licence matters.** CPython's test data is under the PSF licence, which
permits redistribution. A Kaggle dataset usually carries its own licence
(CC0, CC-BY, or the dataset author's terms) that must be checked before
committing a slice of it.

### What CPython requires for its tests to pass

From `https://docs.python.org/3/library/test.html`:

**"The goal for regression testing is to try to break code."** The
documented guidelines:

| Guideline | What it means for gpython |
|---|---|
| Exercise all classes, functions and constants, including private code | Whitebox testing is preferred over blackbox |
| Test all possible values, including invalid ones | Edge cases matter more than happy paths |
| Exhaust as many code paths as possible | Tailor input to the branches |
| Add an explicit test for any bug found | A regression test per bug |
| Clean up after the tests | Close and remove temporary files |
| Verify an OS condition before testing it | Skip rather than fail |
| Import as few modules as possible, as soon as possible | Minimises side effects |
| Maximise code reuse | Share helper functions across tests |

**The naming conventions CPython requires**, which gpython should follow
when porting CPython's tests:

- The test module is named `test_<module>`.
- The test methods start with `test_` and end with a description.
- **No docstring on the test method.** "A comment (such as `# Tests function
  returns only True or False`) should be used to provide documentation for
  test methods. This is done because documentation strings get printed out if
  they exist and thus what test is being run is not stated."

**The stdout-comparison style is deprecated.** "Some older tests are written
using a 'traditional' testing style that compares output printed to
`sys.stdout`; this style of test is considered deprecated."

**This is directly relevant to gpython.** gpython's `pytest.RunScript` is
*exactly* the deprecated stdout-comparison style. When porting CPython's
tests, prefer `unittest`-style asserts over golden-file comparison, and
reserve golden files for cases where there is no natural assertion.

**CPython's test support modules.** 28 modules under `Lib/test/support/`.
The ones a gpython port would need first:

| Module | Purpose |
|---|---|
| `test.support` | The core: `skip`, `requires`, `run_test`, `check_impl_detail` |
| `test.support.import_helper` | `isolated_modules`, `temp_dir`, `CleanImport` |
| `test.support.os_helper` | `temp_dir`, `environ_context` |
| `test.support.script_helper` | `assert_python_ok`, `assert_python_failure` |
| `test.support.isolation` | `run_isolated` |
| `test.support.testcase` | `PythonTestCase`, `MissingModulesTestCase` |
| `test.support.typing_helper` | `TypeIgnore`, `assertTypeEqual` |
| `test.support.bytecode_helper` | `assertBytecode` |

**`assertBytecode` is the one to port first.** CPython's
`test.support.bytecode_helper` compares the exact bytecode of a function
against an expected instruction list. That is a stricter version of gpython's
compile golden data, and it is exactly the tool needed to verify the
3.12+ compiler changes.

**`test.support` has a `Lazy imports` section** in the 3.15 documentation,
which is new and relevant to the PEP 810 work.

### The `regrtest` package

`Lib/test/regrtest.py` is now a 1,300-byte shim. The real implementation is
the `Lib/test/libregrtest/` package: 24 modules.

| Module | Purpose |
|---|---|
| `main.py` | The entry point |
| `cmdline.py` | Argument parsing |
| `findtests.py` | Test discovery |
| `runtests.py` | The serial runner |
| `run_workers.py` | The parallel runner |
| `worker.py` | A worker process |
| `single.py` | Running a single test |
| `testresult.py`, `results.py`, `result.py` | Result types |
| `utils.py` | `get_test_dir`, `setup_centroid`, `cleanup_tempdir` |
| `filter.py` | Test selection by keyword |
| `logger.py` | Logging |
| `parallel_case.py` | A test in parallel mode |
| `refleak.py` | Reference-leak detection |
| `pgo.py`, `tsan.py`, `save_env.py`, `setup.py` | Build and profiling support |
| `win_utils.py` | Windows-specific |

**The mechanism a gpython port would need** is `utils.get_test_dir()` and
`single.py`'s output comparison: run the test, capture stdout and stderr,
compare against the expected. That is what gpython's `pytest.RunScript`
already does, in a simpler form.

### The checklist for adding a new stdlib module's tests

1. Create `stdlib/<module>/<module>_test.go` with the standard 13-line
   body, in `package <module>_test`.
2. Create `stdlib/<module>/testdata/test.py` with the licence header, then
   a `doc` marker, then prints and asserts.
3. Generate `stdlib/<module>/testdata/test_golden.txt` **from CPython
   3.15**, not from gpython.
4. If the module needs a data file, put it in `testdata/` and reference it
   with a path relative to the test's working directory.
5. Follow CPython's test guidelines: name the test method `test_<thing>`,
   use a comment not a docstring, and test the invalid cases.
