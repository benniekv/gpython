# 00 - Hard Engineering Requirements

## Overview

These are the non-negotiable rules for any work on this repository. They are
not style preferences. They are requirements, and they override any other
guidance in this spec set, in `HERMES.md`, in `CONTRIBUTE.md`, or in an
individual task request.

They exist because of a specific failure mode: an agent that "fixes" a
failing test by editing the test, or that leaves code undocumented and
untested, produces a repository that looks green and is wrong.

**These four rules are absolute:**

1. **Always add documentation to all code created or modified.**
2. **Always add tests. Never modify tests and code at the same time.**
3. **A failing test is a good outcome. Diagnose it with the person; never fix
   it automatically.**
4. **All code must be tested unless it is documented as untestable. Only a
   person, together with the agent's guidance, can declare code untestable.**

## Spec

### Rule 1 - Always add documentation to all code created or modified

**Every function, type, method and non-obvious block of code that you create
or modify must carry documentation.**

What "documentation" means here:

| The code | The documentation |
|---|---|
| An exported Go identifier | A doc comment starting with the identifier's name, per Go convention |
| An unexported identifier whose behaviour is not obvious | A `//` comment stating what it does |
| A non-trivial block inside a function | A `//` comment stating why the block is there, not what the code says |
| A new file | The two-line BSD copyright header, plus a package comment if the package has none |
| A new test | A comment stating what behaviour is under test, per CPython's convention of a comment rather than a docstring |
| A modified existing function | Update its documentation so it still describes what the function now does |

**Documentation that has become wrong is worse than no documentation.** If
you change a function's behaviour, its doc comment must change with it. A
doc comment that contradicts the code is a defect.

**The house style for the doc comment**, measured across the 91 non-test
`.go` files: 189 of 206 exported functions (92%) have a preceding comment.
The dominant style is a fragment describing the identifier, starting with a
capital letter and not ending with a period:

```go
// Compile the program in the file prog to code in the module that is returned
func compileProgram(t testing.TB, prog string) (*py.Module, *py.Code) {
```

A full sentence with a period is also acceptable when the comment explains
something rather than naming something:

```go
// The golden files are the test oracle, and they were generated by
// CPython 3.4. Regenerating them from gpython would bake the 3.4
// behaviour in as the new expected result.
```

**Do not document what the code obviously says.** A comment that restates
the code is noise. Document the contract, the reason, and the non-obvious
consequences.

**For Python code**, follow CPython's convention, which this repository
already uses: a `"""..."""` docstring for a module or function, and a plain
`#` comment for a test method. CPython's own test guidelines say a test
method must **not** have a docstring, "because documentation strings get
printed out if they exist and thus what test is being run is not stated".

### Rule 2 - Always add tests, and never modify tests and code at the same time

**Two halves, and the second half is the important one.**

**First half: always add tests.** Every behaviour change comes with a test.
The test goes with the change, in the same commit, so that the commit is
self-verifying.

**Second half: never modify tests and code at the same time.** A commit
changes either the production code or the tests. Not both.

The reason is reviewability. When a commit touches both, a reviewer cannot
tell whether the code changed to satisfy the test, or the test changed to
satisfy the code. Splitting them makes the intent unambiguous:

| Commit | Contents |
|---|---|
| 1 | The code change, with its new tests |
| 2 | The test change, when a test was genuinely wrong |

**A commit that changes only a test is a red flag and needs a clear
explanation in its message.** It means one of:

- The test encoded the wrong expectation. Then the commit message must say
  what was wrong and why.
- The test is being updated for a deliberate change in Python semantics. Then
  the commit message must say so, and it should follow a code change
  commit.

**The golden files are a special case, and the rule still applies.** The
compile, symtable and grammar golden data are generated from CPython, not
from gpython. Regenerating them is a **test** change, so it is its own
commit, and it must state which CPython version produced it.

**Never regenerate golden files with the `-regen` flag as part of a code
change.** That would rewrite the oracle from gpython's own output and bake
the current behaviour in as correct. The golden files come from CPython.

### Rule 3 - A failing test is good; diagnose it with the person, never fix it automatically

**A failing test is a successful outcome when it reveals a real defect.** It
is the test doing its job.

When a test fails:

1. **Stop.** Do not edit the test. Do not edit the code to make it pass.
2. **Report it.** Say which test failed, what it expected, what it got, and
   what you believe the cause is.
3. **Investigate with the person.** Present the evidence: the failing output,
   the diff, the relevant source, the CPython behaviour that establishes the
   correct answer.
4. **Agree on the fix.** Then implement it, as a code change with its own
   tests.

**What is forbidden:**

| Forbidden | Why |
|---|---|
| Deleting a failing test | Destroys the evidence and the coverage |
| Weakening an assertion to make it pass | Turns a real defect into a hidden one |
| Adding a skip to a failing test | Same, but with a comment that makes it look deliberate |
| Editing the golden file to match the wrong output | Destroys the oracle |
| Loosening a test to "match the implementation" | Inverts the purpose of the test |
| Any automated "fix the failing test" loop | See below |

**The reason for the prohibition on automated fixing.** An agent that
iterates "run the tests, adjust the code until they pass" will converge on
*something that passes*, not on *something that is correct*. The two are
different, and only a person who understands the intent can tell them
apart. The agent is good at finding and explaining failures. The person
decides what the correct behaviour is.

**The exception: a test that fails for a documented reason.** If a test
fails because of a known, recorded limitation, that is not a new failure.
It should already be marked. The `py/tests/*.py` files use `# FIXME` for
this, and there are 155 `TODO`/`FIXME` markers across the Go sources.

### Rule 4 - All code must be tested, unless it person documents it as untestable

**Every piece of code you create or modify needs test coverage.**

"Untested" means: no test exercises its behaviour. A test that merely
imports the package does not count.

**Code that genuinely cannot be tested must be documented as untestable, and
that documentation is a joint decision.** The agent may identify a candidate
and explain why it is hard to test. **Only the person, working with the
agent's guidance, can declare a piece of code untestable.** The agent does
not make that call alone.

**The documentation must say what it is**, so a reader can judge the
decision. Something like:

```go
// Untestable: this function's only observable effect is a write to the
// interpreter's stderr, which the test harness captures but cannot
// assert on without a golden file that would be brittle across platforms.
```

**A bare `// TODO: add tests` is not documentation of untestability.** It is
an admission that the work is incomplete.

**The interaction between rules 3 and 4.** If you write code and cannot test
it, do not skip the test and move on. Bring it to the person, with your
reasoning, and let them decide. That is a conversation, not a decision you
make silently.

### How the rules apply to the 3.15 upgrade work

The upgrade is where these rules bite hardest, because it is a large change
to a codebase with a strict oracle.

| Situation | What the rules require |
|---|---|
| Implementing PEP 634 pattern matching | One commit: the AST, grammar, compiler, VM changes, plus the new golden-file cases. The grammar and compile golden data are **regenerated from CPython 3.15** in a **separate commit**. |
| The compile golden data changes 400 lines because `ast.dump` changed | That is a test-only commit. It must say "regenerated from CPython 3.15.2". |
| A new stdlib module needs a test | `stdlib/<mod>/testdata/test.py` and `test_golden.txt`, the golden file generated from CPython 3.15. |
| A `py/` object method needs a test | A case in `py/tests/<feature>.py`. |
| gpython cannot yet parse CPython 3.15 source | Document it, and say so in the commit message. Do not weaken the test that caught it. |
| A PEP turns out to be infeasible in the time available | Raise it with the person. Do not silently narrow the test. |

### The commit-splitting rule in practice

A change that would normally be one commit becomes two or three:

```
py: implement PEP 634 pattern matching

Add the nine Match* AST node types, the match/case grammar rules, the
compiler support and the VM opcodes. The compile golden data is
regenerated separately, because it is test data.

py: regenerate compile golden data from CPython 3.15.2

The compile_test.py input list gains 12 pattern-matching cases and the
generated data is rebuilt against CPython 3.15.2. This is a test-only
change: no production code is modified.
```

The rule is simple to check: **does the diff touch a `_test.go` file, a
`tests/` directory, a `testdata/` directory, or a `*_data_test.go` file?**
If yes, the commit is a test commit, and it must not also touch production
code.

### The definition of done

A piece of work is done when:

1. The code is documented per rule 1.
2. The behaviour is tested per rule 4, or documented as untestable by
   agreement with the person.
3. The tests pass, **or** a failure has been reported and is being
   investigated with the person.
4. The commit respects rule 2: code and tests are not in the same commit.
5. The commit message says what was done and why.

**A work item is not done because the tests are green.** It is done when the
tests are green because the code is right, and the person has reviewed it.
